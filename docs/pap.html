Principal Agent Protocol.
The internet needs a lifecycle for agents.

Without a trust protocol, agents accumulate permissions forever, platforms capture everything, and sessions never die. PAP gives agents a hard lifecycle — and gives humans actual cryptographic authority over them.

Why PAP exists

Five things that go wrong.
Five fixes in the protocol.

Each invariant targets a specific failure mode of the agentic internet at scale. They’re not features you can configure — they’re structural properties baked into every compliant implementation.

01
Agents work for platforms, not for you

Today’s AI agents hold your credentials, learn your behavior, and answer to a vendor’s terms of service — not yours. PAP makes your hardware key the only thing that can authorize an agent. No platform, vendor, or intermediary can act in your name without a mandate cryptographically signed by your device. Delegation flows down from you. Never up from a platform.

WebAuthn · FIDO2 · hardware-bound root of trust
02
Sessions that never die drain the internet

Book one flight, and a naively-designed agent keeps running — holding connections, burning compute, accumulating permissions. At a billion users, that background swamp is a massive overallocation problem no platform will voluntarily fix. PAP mandates carry a hard TTL. In Papillion, the orchestrator renews TTLs while you’re actively working on the canvas. The moment you step away, the session winds down. Agents live exactly as long as you need them. The internet doesn’t carry their dead weight.

JWT · hard TTL · internet resource governance
03
Linked sessions become behavioral fingerprints

Ad networks built billion-dollar businesses by linking your browser sessions across sites. Agent platforms will do the same if given the chance — one session becomes a fingerprint, sessions accumulate into a behavioral profile, the profile gets sold. PAP issues a fresh DID:key identity for every agent session, derived in-memory and never reused. No session can be linked to any other. There is no thread to pull.

DID:key · Ed25519 · per-session · unlinkable
04
All-or-nothing APIs leak everything

To book a flight through most AI integrations today, you authorize the app to read your email, calendar, contacts, and location history — because the API is all-or-nothing. PAP makes selective disclosure a first-class protocol feature. The travel agent gets your destination and your budget. It doesn’t get your name. It doesn’t get your history. It doesn’t get anything it can sell. Agents get exactly the inputs they need to function. Nothing more.

SD-JWT · W3C VC · minimum-necessary disclosure
05
Value-bearing receipts are surveillance logs

Without receipts, agents can claim they did things they didn’t — or deny things they did. So you need receipts. But a receipt containing values is a surveillance log: aggregate a billion of them and you have a behavioral database nobody consented to. PAP receipts record property names, never values. “Destination was disclosed” — not “destination was Tokyo.” The receipt is co-signed by both the principal session key and the agent. Proof that the right thing happened. Not a profile of what it was.

co-signed · property-names-only · accountability without surveillance
06
Discovery without a standard becomes a silo

Without a common format for capability advertisement, agents can only find each other within the same platform. Every vendor builds a walled garden. Every integration is a custom bilateral contract. PAP defines a signed JSON-LD service advertisement any registry can index — no central authority required. Agents publish what they can do and what they need. Any compliant directory can list them. In Papillion, the visual composer lets you browse available agents and drag them into workflows without writing a line of code. Crystalis is the self-hostable reference registry — run your own, federate with others, or stay entirely private.

JSON-LD · Schema.org · federated registry · visual composer
Implementation

No novel cryptography.

PAP is composed entirely from established standards. Nothing invented, nothing proprietary. Every layer has a well-understood security model and existing tooling.

Layer Standard Role in PAP
Trust Root WebAuthn/FIDO2 Hardware-bound principal identity. Signs the initial Mandate chain.
Identity DID:key (Ed25519) Ephemeral session identities. Derived fresh per session, verifiable without a registry.
Authorization JWT + custom Mandate schema Signed delegation with scope, constraints, TTL. Chain-verifiable from principal to agent.
Selective Disclosure SD-JWT / W3C VC Agents receive only the claims they need. Principal controls disclosure at issuance time.
Service Advertisement JSON-LD + Schema.org Agents advertise capabilities as signed JSON-LD service documents. Verifiable before contact.
Transport HTTP/TLS, WebSocket Standard transport. PAP is transport-agnostic; TLS handles channel confidentiality.
Federation PAP Federation Protocol Peer node discovery and cross-registry capability lookup. Implemented in pap-federation.
Rust Reference Implementation

Multi-crate monorepo.

The reference implementation lives in crates/ — eight focused crates with clear boundaries. Use only what you need.

pap-core

Mandate engine, session lifecycle, trust chain validation. The protocol heart.

pap-did

DID:key generation, resolution, and document handling. Ed25519 ephemeral identities.

pap-credential

SD-JWT and W3C VC issuance, verification, and selective disclosure.

pap-transport

HTTP and WebSocket transport layers. Async, pluggable, TLS-aware.

pap-federation

Node discovery and peer federation protocol. Powers Crystalis federation.

pap-marketplace

Agent registry, capability advertisement parsing and indexing.

pap-webauthn

WebAuthn credential binding, attestation, and principal key derivation.

pap-python

PyO3 bindings. Full protocol surface available from Python.

Quick Start

Add PAP to your agent.

Three steps to a mandate-authenticated agent session. See the integration guide for the full walkthrough.

1
Add the dependency

Add pap-core to your Cargo.toml. For Python, pip install pap.

2
Bind your principal

Load or register a WebAuthn credential. This becomes your hardware-bound root of trust.

3
Issue a mandate and open a session

Sign a Mandate with the scope, constraints, and TTL your agent needs. Open the session. The protocol handles ephemeral DID rotation, selective disclosure, and receipt generation automatically.

src/main.rs 
use pap_core::{Principal, Mandate, Session};
use std::time::Duration;

// 1. Load your hardware-bound principal
let principal = Principal::from_webauthn(&credential)?;

// 2. Define exactly what the agent may do
let mandate = Mandate::builder()
    .scope(["travel:search", "travel:book"])
    .constraint("maxBudget", 1500.0)
    .constraint("destination", "TYO")
    .ttl(Duration::from_secs(1800))
    .build()?;

// 3. Open an ephemeral session
//    DID rotation, SD-JWT, receipt — all automatic
let session = principal.authorize(mandate)?;
let result  = session.run(&flight_agent).await?;
Working Examples

Full protocol surface coverage.

Six runnable examples in examples/ demonstrating every major protocol feature.

search

Minimal capability advertisement, mandate issuance, and single-agent query. The hello-world of PAP.

cargo run --example search
travel-booking

Multi-constraint mandate: destination, budget, cabin class, maxStops. Shows receipt generation.

cargo run --example travel-booking
delegation-chain

Orchestrator delegates to downstream agents with narrowed scope. Validates the full trust chain.

cargo run --example delegation-chain
payment

Payment action with value constraints and two-phase confirm. Co-signed receipt with amount as property name only.

cargo run --example payment
networked

Two agents on separate nodes. Exercises the transport layer, registry lookup, and DID resolution.

cargo run --example networked
federated

Cross-registry capability discovery via the PAP federation protocol. Two Crystalis nodes talking.

cargo run --example federated
