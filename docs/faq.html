PAP v0.x is explicitly consumer-first. The trust anchor is a device-bound Ed25519 keypair held by a single human principal (crates/pap-did/src/principal.rs). Mandate delegation chains downstream agents, not other principals — there is no native concept of organizational roles, service accounts, or delegated authority hierarchies between humans.

Employee offboarding, SCIM provisioning, and IdP-backed identity (Okta, Azure AD, Ping) are not in the codebase today. The M-of-N social recovery mechanism uses banks/notaries as recovery trustees, which reintroduces institutional trust at the most sensitive point in the protocol — something worth naming honestly.

What's needed: A PAP-ORG profile that maps organizational roles to mandate issuance authority and describes how PAP can sit behind an existing enterprise IdP. This is an open design question, not a shipping feature.

In healthcare and financial services, which properties were accessed is frequently PHI or material non-public information in its own right.

Each Papillon instance and Chrysalis node runs its own embedded OHTTP relay. Baur Software does not operate a relay. There is no external relay operator to capture. The relay is colocated with your own deployment — decentralized by topology, not just by policy.

In pap-transport/src/ohttp.rs, relay_url is typed Option<String>: when absent the protocol falls back to a direct connection, so removing the relay degrades privacy but never breaks the handshake. The core privacy guarantees — SD-JWT selective disclosure, ephemeral session DIDs, deny-by-default mandates — do not depend on OHTTP.

One honest caveat: the current HPKE implementation is a placeholder ("simple implementation" per code comments). Full cryptographic unlinkability per RFC 9458 is the target; the relay architecture is already correct.

Vouch-based peer admission. Joining the Chrysalis mesh is not free — it requires existing trusted peers to stake their reputation on you. pap-federation/src/registry.rs enforces:

3 vouches required to register a new peer. Each existing peer may issue at most 3 vouches per year — a rate budget that makes flooding expensive. A peer must be registered for at least 90 days before it can vouch for anyone. New peers enter a 60-day probationary period with limited permissions.

Diverse trust paths (require_diverse_paths) are specified in the policy struct and are being enforced now — ensuring N vouchers don't all route through the same small set of ancestors, preventing a captured clique from bootstrapping unlimited new peers.

This is a social-graph approach rather than proof-of-stake or proof-of-work. The rate constraints make a Sybil flood expensive in terms of calendar time and peer relationships, not compute or tokens.

Schema.org is a collaborative, open-community project founded by Google, Microsoft, Yahoo, and Yandex to create a shared structured-data vocabulary. The schema is community-governed; contributions come from across the web industry. Google drives significant adoption through rich-result support, but it does not have unilateral control over the vocabulary.

That said, there is a real practical constraint: all PAP action types and property references today are hardcoded Schema.org strings. Any capability that doesn't fit the current vocabulary — financial compliance actions, FHIR operation vocabulary, laboratory protocol steps — requires either a Schema.org extension proposal or a protocol-level change. There is no vocabulary extension mechanism in the current codebase or specification.

Schema.org is the right baseline for interoperability across general web agents. Domain-specific verticals will need extension points.

Scope containment is cryptographically enforced at every delegation step. pap-core/src/scope.rs contains() verifies that a child mandate's action set is a strict subset of its parent's. mandate.rs verify_chain() binds each delegation to its parent by hash — you cannot forge a valid chain that expands scope. TTL cannot exceed the parent mandate either.

Auto-approval has a further constraint: it triggers only when requires_disclosure.is_empty() (canvas.rs). No action that requires any disclosure from the principal can be auto-approved — the user always sees the approval gate.

The narrower residual risk: a sequence of zero-disclosure sub-actions that individually pass auto-approval could collectively achieve an effect that a single equivalent request would have surfaced for explicit consent. The cryptographic scope bounds still apply to each step; the gap is at the semantic composition layer.

The premise needs clarifying. Papillon's intent router (crates/papillon-shared/src/intent.rs) is a deterministic 600-line keyword lookup table — 181 rules across 23 agents, no LLM in the path. A user query is keyword-matched, cleaned, and dispatched to a specific catalog agent. The 6-phase PAP handshake then enforces scope cryptographically. There is no LLM between the user's words and the mandate boundaries.

An LLM appears in exactly two places, both after the handshake:

On-Device AI fallback — when no keyword rule matches, the query goes to an on-device model running locally (Candle, never a cloud API). The query arrives in a delimited [INST]…[/INST] conversation role; the preamble is the user's own memex history (trusted data), not external content.

Pipeline Synthesizer — an optional post-execution node that merges multi-agent results using the local model. This runs after all disclosure and execution is complete; it cannot retroactively change what was disclosed.

Prompt injection risk is none in the main handshake path, and low in the local LLM path — the model is on-device, sandboxed, and operates with zero disclosure requirements of its own.

Measured p50 loopback numbers from CI (benches/baseline.json): full session lifecycle 130 µs (target <20 ms), depth-3 mandate chain verification 138.5 µs. The benchmark suite uses Criterion with a 30% regression gate on p50.

p99 is not yet in the suite. A p50 of 130 µs is entirely compatible with a p99 of several milliseconds under real network conditions — and tail latencies are where distributed systems actually fail. p99 benchmarks are being added to benches/benches/protocol.rs with corresponding CI regression guards.

Two failure modes that remain unspecified:

Network partition mid-handshake: fail-open is a security catastrophe for financial or medical agents; fail-closed may be unacceptable for high-availability systems. The behavior is undefined in the current specification.

TTL expiry during handshake: a mandate that expires mid-flight through a 6-phase sequence has no defined recovery path.

Receipts contain property references only, never values (pap-core/src/receipt.rs: Vec<String> of strings like "schema:Person.name"). Each party holds their own copy locally — receipts are never stored by a platform. There is no central data controller.

The specific tensions with each framework:

GDPR Article 17 (right to erasure): Receipts are co-signed by both parties and stored in an insert-only SQLite database (episode_db.rs has no delete API). Immutability is a deliberate accountability design. Who holds deletion authority over a receipt both parties signed is not defined — this is a real open question for regulated deployments.

HIPAA Minimum Necessary: Property type references in receipts can themselves constitute PHI. Knowing MedicalCondition was disclosed reveals a medical relationship even without the value. Regulated healthcare deployments will need a PAP-HIPAA profile.

MiFID II / Dodd-Frank: Ephemeral session DIDs and session-close forgetting conflict with 7-year trade reconstruction obligations. Financial agent transactions in regulated markets need explicit carve-outs the spec doesn't yet define.

Full PyO3 bindings ship today. crates/pap-python/src/lib.rs (1,595 lines) exposes the complete PAP API with both blocking methods and async variants for all transport steps. The async path uses PyO3 0.24 experimental-async, which releases the GIL during await — making concurrent handshakes work correctly in asyncio agent pipelines without to_thread() wrapping.

A comprehensive integration guide covers LangChain, CrewAI, and MCP with 1,293 lines of annotated examples: docs/integration-guides/langchain-crewai-mcp.md. The TypeScript equivalent — packages/pap-ts — is a pure native async implementation with zero Rust dependency, for reference.

The remaining friction: the package is not yet on PyPI (build via maturin develop) and debugging across the FFI boundary is harder than debugging pure Python at the POC stage.

What's next: A native pure-Python pap-py package — zero build step, pip install pap — parallel to pap-ts. For teams that want zero-friction trial integration, FFI overhead is a worse tradeoff than a small performance gap.
