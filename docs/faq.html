PAP v0.x roots trust in a device-bound WebAuthn keypair held by a human. This is intentional for the consumer and freelancer personas the protocol was designed for first — and it is an honest limitation for enterprise deployments.

In an enterprise, mandates derive from role-based authority that persists beyond individuals. Employee offboarding, service-account rotation, and delegated authority hierarchies (manager → report) are not natively expressed in the current mandate structure. Every enterprise already has an IdP (Okta, Azure AD, Ping) that PAP does not integrate with today.

The M-of-N social recovery mechanism (banks / notaries) is designed for personal key recovery — it reintroduces institutional trust at exactly the point PAP claims to eliminate it, which is a real tension.

What's planned: A PAP-ORG profile that maps organizational roles to mandate issuance authority and defines how PAP can sit behind an existing enterprise IdP without requiring every action to be gated on a human-held keypair. This is an open design question, not a shipping feature.

OHTTP (RFC 9458) is listed in the PAP stack as an optional privacy enhancement for cloud request unlinkability. Anyone can operate a relay. The spec does not define relay governance, diversity requirements, or what happens to the unlinkability guarantee when no relay is available.

This is structurally equivalent to the CA cartel problem that DIDs were designed to avoid — PAP displaces the centralization risk to the network layer without acknowledging the displacement. If a small consortium (including Baur Software) becomes the de facto relay operators, the protocol re-centralizes at exactly the layer the rest of the design was built to avoid.

The honest framing: OHTTP is an optional enhancement. The core protocol's privacy guarantees (SD-JWT, ephemeral session DIDs, deny-by-default mandates) do not depend on OHTTP. Relay diversity requirements — analogous to Tor's guard node requirements — are an open spec gap for future work.

Currently: nothing beyond Ed25519 signature verification. The federated registry uses peer-to-peer pull sync and accepts any signed advertisement from any valid keypair. Publishing a signed agent advertisement is computationally and economically free — there is no proof-of-stake, reputation score, or endorsement mechanism.

DID document rotation under key compromise is also unaddressed. If a Chrysalis node's controlling keypair is compromised, existing mandates that trusted that DID become invalid, but the spec does not define revocation propagation across the mesh.

Network effects compound this: the most-populated Chrysalis mesh becomes the de facto authority. A dominant cloud provider refusing to peer with independent nodes replicates the ActivityPub / email centralization pattern the protocol is designed to avoid.

What's planned: A lightweight reputation layer — proof-of-uptime, endorsement by N existing trusted nodes, or a signed transparency log (similar to Certificate Transparency). The Chrysalis capture test must apply to the registry layer, not just the handshake layer.

Yes — this is a known attack class (confused deputy) and PAP does not fully address it yet. Auto-approval tiers are principal-authored policies that cannot exceed mandate scope at the individual action level. But composition is not checked.

A sophisticated orchestrator that can observe which actions trigger auto-approval versus which require explicit consent learns the principal's approval behavior profile — a covert channel that persists across sessions. More directly: a sequence of N individually auto-approvable sub-actions can collectively achieve what a direct request for action X would have been denied.

The receipt system records property references and approval policy invocations, but provides no mechanism for the principal to reconstruct a multi-step action sequence after the fact.

What's planned: A semantic action composition constraint in the mandate spec. If a sequence of N actions collectively constitutes prohibited action X, then approval of the sequence requires the same consent level as direct approval of X. This requires formal action composition semantics — non-trivial, but necessary for the protocol to be sound against adversarial orchestrators.

Correct. This is the most important limitation to understand clearly. PAP's cryptographic controls govern what data is disclosed over the wire to downstream services. They do not govern what the LLM orchestrator does with its internal context.

A malicious API response crafted to inject instructions can manipulate the orchestrator into expanding scope, requesting additional disclosures, or bypassing auto-approval policies — without violating any cryptographic constraint. The LLM has already processed the principal's full context. A successfully manipulated orchestrator could paraphrase or embed principal context into request payloads in ways the protocol's controls do not catch.

PAP's own critique of competitors — "sandboxing constrains what an agent can do, not what it can see" — applies equally to PAP's orchestrator when the orchestrator is an LLM.

What's planned: A PAP-ML section in the specification that formally frames the LLM orchestrator as an untrusted sub-component within the trust hierarchy — even though it holds principal context. This means defining instruction hierarchy enforcement requirements as a PAP compliance requirement for orchestrator implementations. No other agent protocol addresses this. That makes it a genuine differentiation opportunity, not just a gap.

Unknown — this is an open gap in the benchmark suite. Published benchmarks cover single-session loopback at p50 (sub-20ms). Multi-hop p99 and p999 latencies in real network conditions have not been measured and are not in the CI regression suite.

For a 3-hop production chain: N × 6 handshakes plus N cryptographic operations chain serially. A p50 of 20ms is entirely compatible with a p99 of 500ms in any network with packet loss. Tail latencies are where distributed systems actually fail — constraining only p50 is insufficient for production readiness claims.

Two additional failure modes are undefined in the current specification:

Network partition mid-handshake: Fail-open is a security catastrophe for financial or medical agents. Fail-closed may be unacceptable for high-availability applications. Neither behavior is specified.

TTL expiry during handshake: A TTL=30s mandate that expires during a 6-phase handshake produces no defined recovery path in the current specification.

What's planned: p99 benchmarks added to the benchmark suite with CI regression guards. A Session Recovery Protocol for network partition scenarios. A PAP Latency Budget Calculator that shows how mandate depth and handshake phases compose for common deployment topologies.

Honestly: regulatory compliance is architecturally unaddressed in the current specification. Here is the specific tension with each framework:

GDPR Article 17 (right to erasure): Co-signed receipts create a mutual accountability record. Who holds deletion authority over a receipt both parties signed? The spec doesn't define this. The receipt design may be structurally incompatible with right-to-erasure as currently specified.

HIPAA Minimum Necessary: Property references in receipts can constitute PHI. Knowing that a MedicalCondition property was disclosed reveals the existence of a medical relationship, regardless of whether the value is hidden.

MiFID II / Dodd-Frank: Ephemeral sessions with session-close forgetting directly conflict with 7-year trade reconstruction obligations. PAP as designed cannot be used for financial agent transactions in regulated markets without carve-outs the spec doesn't yet define.

MiCA / FinReg: Ecash and Lightning payment proofs embedded in mandates may constitute unlicensed payment facilitation in the EU, UK, and several US state jurisdictions.

What's planned: A PAP Regulatory Conformance Matrix mapping protocol features to specific regulatory frameworks, identifying where PAP profiles or extensions are needed. This is a go-to-market strategy artifact — not a blocker — but serious enterprise buyers will require it before procurement.

Today: PyO3 C FFI wrappers around the Rust core — and that's a real friction point. The agentic AI ecosystem PAP is targeting (LangChain, LlamaIndex, AutoGen, CrewAI, smolagents) is Python-first.

PyO3 async support is immature. GIL interactions with Python's async frameworks (asyncio, trio) create unpredictable blocking in multi-threaded agent pipelines. Integrating PAP into an async LangChain agent graph requires asyncio.to_thread() wrapping for every PAP operation, which serializes what should be concurrent handshakes.

Debugging across the FFI boundary in production is significantly more painful than debugging a native Python implementation. This creates adoption friction at the POC stage — precisely when developer experience determines whether a protocol gets trial-deployed or abandoned.

What's planned: A native pure-Python implementation of the PAP handshake — parallel to pap-ts, which is a pure TypeScript implementation with no WASM dependency. The Rust core remains the reference implementation and performance-critical path. Python adoption velocity matters more than zero-FFI-overhead for most enterprise integration use cases.
