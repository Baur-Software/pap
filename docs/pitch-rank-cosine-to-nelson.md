## The real question

Your paper shows rank-cosine + RRF recovers BM25 + dense within tight margins on 207k arXiv abstracts and three BEIR corpora — all document retrieval at scale, with independently-authored texts and binary relevance judgments.

PAP's intent routing is a different task. Our catalog is **309 agents** (not 207k documents), the descriptors are **short structured strings** (~50 tokens, many sharing boilerplate), the relevance judgments are **multi-label action-type routing** (not binary), and **97% of agents cluster in just 2 action types** (SearchAction=179, FindAction=113). The routing problem is closer to a binary decision than a multi-class retrieval problem.

The honest question is: **does rank-cosine add measurable signal beyond BM25 at this scale and structure, or does BM25 already suffice?** If it adds signal, that's a transfer claim your §5.6 can't currently make — different task, different scale, different relevance regime. If it doesn't, that's a clean negative result that directly addresses your §6 corpus-scope limit with empirical evidence: "rank-cosine does not improve over BM25 at N=309 with structured short descriptors and imbalanced action-type routing." Either answer is publishable. Neither of us can get it alone.

## Why you can't run this yourself

You can clone the catalog (it's open — 309 TOML files in `crates/pap-agents/catalog/`). What you can't get from cloning:

1. **Real query distributions.** Synthetic paraphrase eval queries (your §4.3) are generated by prompting a different model family with the source abstract. That's a controlled distortion of known documents. PAP users type free-form intents into the address bar — "will it rain in paris tomorrow", "i need a place to stay near the louvre", "how big is the react bundle" — and the query distribution is unknown, long-tailed, and genuinely paraphrastic rather than synthetically so. After deployment, we can provide anonymized query logs with the routing outcome (which action group won, whether it was correct per user follow-up behavior). You can't simulate this.

2. **A second implementation in a different language.** Your pipeline is Python/NumPy. A Rust implementation that produces the same rankings from the same inputs is an independent validation — not of the concept (which is trivially reproducible from the math) but of the specific numerical behavior under tied ranks, short vectors, and FP32→rank edge cases. If both implementations agree, that's a non-trivial reproducibility signal. If they disagree, that's worth finding.

3. **A structured routing task where the failure mode is known.** You already know BM25 collapses on paraphrase (0.695 R@10). PAP's Level 2 currently falls through to Level 3 (on-device AI) on those queries — we can measure the fallthrough rate, which is the real-world BM25 failure signal. Your paper measures failure as R@10 against ground truth; we measure it as the rate at which the system escalates to a slower, more expensive path. Same phenomenon, different operationalization.

## The encoder problem (honest version)

Rank-cosine requires an encoder. Your eval uses Harrier-OSS-v1-0.6B (1024-dim, L2-normalised). A 0.6B model cannot run in WASM, and PAP's browser build is WASM-only.

Here's how it would actually work in our architecture:

- **Catalog agents**: Rank vectors are pre-computed at catalog build time. The encoder runs once per agent on the build machine — this is already our pattern (the 309 TOML files compile to a static JSON blob shipped in the WASM binary). No encoder in the browser. The rank vectors (or RankQuant buckets) are just data in the static catalog.

- **User queries**: The query needs encoding to produce the FP32 vector for the asymmetric rank-cosine score (your §3.3). This happens on the Tauri desktop side, which has native compute and can run a small encoder locally. In the WASM-only browser build, there is no query encoder — the rank-cosine channel is simply absent and the system falls back to BM25 alone, exactly as it does today.

This is the existing **AI-optional degradation pattern**: the system works without the enhancement layer, and the enhancement layer improves it when available. Level 3 (on-device AI) is already optional — if no local model is configured, the system routes without it. Rank-cosine would follow the same pattern: available on desktop (where an encoder runs locally), unavailable in browser (where it can't), and the BM25 baseline is unchanged in both cases.

I initially called the encoder "load-bearing" — that was wrong in PAP's context. In your paper, the encoder is load-bearing because removing it collapses R@10 to 0.33. In PAP's architecture, the encoder is an optional enhancement: the system works without it, and it works better with it. Your paper proves *how much* better (the +16.9 point gap on paraphrase). That's the right framing — not "the encoder is required" but "the encoder is worth having when you can run it."

## Appendix: Evaluation Against Sources, Competitive Landscape, and Recommendations

*Added 2026-05-18 after comprehensive literature review spanning WTA hashing, quantization, QPP/routing, and learned ranking.*

### A. Source Evaluation

The paper is methodologically rigorous. The self-retraction of the Λ₁ routing estimate (0.894 → 0.862 after M3 audit) and the "what this section is not" disclaimers are strong integrity signals. The statistical testing (paired bootstrap, Wilson CIs, Cohen's h) is appropriate. That said:

| Cited Source | Verdict | Gap |
|---|---|---|
| WTA [4,43] | Partially fair | Scale claim is absence-of-evidence, not evidence-of-absence. WTA lineage (SoftHash 2026, MP-WTA 2026, RACE/SOCKET 2025-26) not cited. |
| TurboQuant [44] | Strongest comparison in the paper | Byte-matched, honest, corpus-conditional caveat reported |
| PQ [20] | Mentioned but not benched | No PQ/OPQ baseline at matched 256 B/vec — the natural storage comparison is absent |
| Grossberg [15] | Honestly acknowledged | Missing the 1-bit sign-cosine ablation (sign vectors scored by cosine, not Hamming) that would clarify whether the advantage is ordinal resolution or cosine scoring |
| Plummer [31] | Decorative | No mechanical connection between feasibility preservation and Λ₁ construction |
| Creative Determinant [37] | Self-cite, undermined by own results | v₀ scalar (Pearson 0.992 with Λ₁) means the graph-theoretic machinery contributes nothing; the theoretical motivation is hollowed out by the empirical finding |
| Faggioli [13] | Underexplored | Should have been a QPP baseline; coherence signals might capture what the Fiedler vector fails to (Pearson 0.029) |
| RankEncoder [35] | Fair | Correctly distinguished |
| RRF [8] | Fair | Standard use |
| **Missing citations** | — | BoI/Magliani 2021 (same rank transform + Spearman Footrule distance), RBH/Kawai 2024 (rank-position hashing for ANN), Ordinal Binary Coding/Liu 2018 (79 citations, preserves ordinal structure into binary codes), LSH for Spearman/Tellez & Chavez 2010, RaBitQ/Gao & Long 2024, ScaNN AVQ/Guo 2020, NQC/Shtok 2012 |

### B. Competitive Landscape — Methods Not Engaged With

**Storage/Quantization**

| Method | Key Idea | Why It Matters vs RankQuant |
|---|---|---|
| **RaBitQ** (Gao & Long, 2024) | 1-bit + random rotation + re-binning, provable error bound for ANN | The B=1 baseline RankQuant needs. Random rotation decorrelates before binarization; RankQuant ranks instead. Which decorrelation strategy preserves more retrieval signal at 1 bit? |
| **ScaNN AVQ** (Guo et al., ICML 2020, 725 citations) | Anisotropic quantization — penalizes error along query direction, ignores orthogonal | Philosophically adjacent to terminal-inference insight ("only some directions matter") but attacks from magnitude side. RankQuant is isotropic; ScaNN is direction-aware. At matched bytes, which captures more of what retrieval consumes? |
| **OPQ at 256 B/vec** | Optimized Product Quantization with learned rotation | The natural byte-matched storage baseline. Absent from the paper. PQ at 8 B/vec (Table 8) is not byte-matched. |
| **Ordinal Constraint Binary Coding** (Liu et al., 2018, 79 citations) | Preserves ordinal relationships into binary codes | Most direct predecessor to RankQuant's core idea. Not cited. |
| **QJL** (Zandieh et al., AAAI 2025) | JL projection + sign bit only, unbiased inner product estimator | Closest 1-bit competitor to RankQuant B=1. Linear (projection + sign) vs. nonlinear (rank transform + bucket). |
| **NVQ** (Tepper & Willke, 2025) | Per-vector non-uniform quantization | RankQuant's bucketing is uniform across dimensions. NVQ shows non-uniform per-vector quantization outperforms uniform in high-fidelity regime. Schema.org-typed descriptors may have multimodal per-dimension distributions where non-uniform bucketing preserves type-separating structure better. |
| **CARVQ** (Gou et al., EMNLP 2025) | Group residual VQ with corrective adaptor at <0.1% overhead | Suggests a "corrective RankQuant" hybrid: rank buckets + learned residual for the error |

**QPP/Routing**

| Method | Key Idea | Why It Matters |
|---|---|---|
| **MAB routing** (Tang et al., AAAI 2025) | Multi-armed bandit selects retrieval strategy per query, adapts online | Directly addresses Λ₁ transfer limitation. Bandit arms = tiers; reward = quality/cost. No per-corpus tuning needed. |
| **Inverse QPP** (Mbarek & Hattab, ACM TOIS 2026) | Frames QPP as inverse regression; Kendall's tau 0.5402 vs forward 0.344 | Significantly better rank correlation for routing decisions. Would improve three-tier threshold selection. |
| **NQC + UEF** (Shtok et al., 2012) | Normalized Query Commitment + post-retrieval features | Classic QPP baseline. Should have been compared. |
| **Coherence-based QPP** (Vlachou & Macdonald, 2023) | Inter-document embedding similarity predicts retrieval effectiveness | Operates on same embedding space as Λ₁ but without eigen-decomposition. Up to 92% accuracy improvement over sparse variants for dense retrieval. |
| **Chifu et al., 2025** | Systematic evaluation: QPP-driven selective processing gives only marginal gains | Validates the Λ₁→v₀ collapse from the other direction. Simple scalar predictors often match complex structural ones. |
| **Early-exit CE** (Busolin et al., 2025) | Exit cross-encoder when intermediate confidence is sufficient | Complementary to Λ₁: Λ₁ gates whether to enter the cascade; early-exit determines how deep to go within it. |

**Reranking**

| Method | Key Idea | Why It Matters |
|---|---|---|
| **Offline CE → LambdaMART distillation** | Run CE at build time, use its judgments as LambdaMART training targets | Closes the paraphrase gap (+5.08 R@10) without needing CE at inference. Fully WASM-compatible. The strongest recommendation for PAP's architecture. |
| **SetEncoder** (multi-doc single-pass) | Encode all candidates in one forward pass; 5-10× faster than standard CE | Most promising architecture for closing paraphrase gap at moderate latency. |
| **monoT5** (T5-base/3B) | Sequence-to-sequence reranking; ~5-20ms latency | The missing middle ground between LambdaMART (0.2ms) and CE (591ms). |
| **MiniLM-L6 distilled** (22M params) | Potentially WASM-compileable via ONNX | Could serve as Level 2.75 for low-confidence paraphrase queries only. |
| **Weighted RRF** | Learn per-system weights instead of fixed k=60 | Lets fusion "route" paraphrase queries toward rank-cosine and keyword queries toward BM25 within the same formula. Low cost, high impact. |

**WTA/Rank-Based Predecessors (Uncited)**

| Method | Key Idea | Why It Matters |
|---|---|---|
| **Bag of Indexes** (Magliani et al., 2021) | Same rank-transform preprocessing, Spearman Footrule (L1 on ranks) as distance | Most direct predecessor. RankQuant's contribution over BoI: Spearman Rho (cosine on ranks) instead of Footrule, plus B-bit bucketing for compression. |
| **Rank-Based Hashing** (Kawai et al., 2024) | Rank positions as hash codes for ANN, no training | Same approach for image retrieval. Not cited. |
| **LSH for Spearman** (Tellez & Chavez, 2010) | Rank vectors in L1/L2 spaces admit standard LSH families | Rank-cosine can use ANN indexing without any novel LSH construction. The sub-millisecond brute-force result is less impressive when standard ANN acceleration is already compatible with the rank representation. |
| **SoftHash** (Zhang et al., ICASSP 2026) | Learnable soft WTA mechanism; gradients flow through hashing | WTA lineage moving toward learned hash functions. Not cited. |

### C. Top 5 Recommendations for the Paper

1. **Add RaBitQ and ScaNN AVQ as byte-matched baselines.** These are the quantization methods most likely to challenge RankQuant's claims. If RankQuant still holds, the paper is much stronger.

2. **Cite and differentiate from BoI, RBH, and Ordinal Binary Coding.** Reviewers will find these. The intellectual lineage should be addressed proactively.

3. **Replace Λ₁ with a GBDT on combined QPP features** (v₀ + NQC + BM25 score gap + bitmap overlap). The spectral machinery adds nothing per the paper's own results; a learned combination of cheaper signals transfers better and is more honest about what's doing the work.

4. **Test offline cross-encoder distillation into LambdaMART.** Run the CE on training data at build time, use its judgments as LambdaMART targets. Closes the paraphrase gap without needing the CE at inference.

5. **Add the 1-bit sign-cosine ablation.** Between Grossberg's sign-Hamming and RankQuant's full-rank-cosine, the untested middle ground (sign vectors scored by cosine) clarifies whether the advantage comes from ordinal resolution or the cosine scoring function.

### D. The Long-Term Opportunity

**RankQuant-aware encoder training.** No published work trains embeddings *for* rank-cosine scoring. All existing encoders are trained for FP32 cosine or Euclidean. A differentiable soft-rank loss that produces representations optimized for rank-cosine consumption would:
- Make the formation side of the thesis directly testable
- Potentially improve RankQuant's B=1 and B=2 operating points
- Be genuinely novel — the gap is empty in the literature

### E. Revised Framing for PAP

The original pitch frames the 309-catalog experiment as "does rank-cosine add signal beyond BM25 at this scale?" The evaluation above suggests a sharper framing:

**The 309 seed is a portability test across task domains.** Nelson proves portability across *corpora* (same task, different domains). PAP proves portability across *task domains* (typed service routing vs. document retrieval). The schema.org type structure is the experimental variable Nelson's corpus doesn't have. That's what makes the transfer interesting regardless of outcome.

PAP's core use case: resolve user intent → craft request with selective disclosure, without an LLM in the loop. The pipeline:
1. Natural-language intent (always a paraphrase)
2. Route to schema.org-typed service via BM25 + rank-cosine RRF (sub-millisecond, no LLM, no FP32)
3. Craft request deterministically from service's schema.org metadata (requires_disclosure, object_types, returns)
4. LLM escalation only when 2-3 fail

The metric that matters for PAP isn't R@10 — it's **LLM escalation rate**. If BM25 + rank-cosine RRF routes 80%+ of intents to the right service without LLM involvement, the expensive component is removed from the default path. Nelson's paraphrase fold predicts this: rank-cosine holds at 0.864 vs BM25's 0.695, meaning ~17% more paraphrase intents resolve without semantic escalation.

The **B=2 bucketing concern is schema.org-shaped**: at D=1024 with B=2, each dimension gets 4 uniform buckets. If schema.org action types concentrate coordinate values (they should — FindAction activates different dimensions than SearchAction), the per-dimension rank distribution is multimodal. Uniform 4-bucket RankQuant could split a type-separating dimension at the wrong boundary. This is where ScaNN's anisotropic insight matters: dimensions that separate schema.org types should get more bucketing resolution. A schema.org-informed bucketing strategy (per-dimension adaptive boundaries based on type distribution) is a PAP-specific contribution that Nelson's paper doesn't address because arXiv abstracts don't have type labels.

## Appendix F: Empirical Results — Portability Test on 309-Agent Schema.org Catalog

*Run 2026-05-18. Full experiment code at `experiments/rank_cosine_portability/experiment.py`.*

### Action-Type Routing Accuracy

| Method | Paraphrase (n=20) | Keyword (n=5) | Title (n=3) | Overall (n=28) |
|---|---|---|---|---|
| BM25 | 0.300 | 0.800 | 1.000 | 0.464 |
| Dense FP32 | 0.600 | 0.600 | 0.667 | 0.607 |
| **Rank-Cosine** | **0.600** | 0.600 | 0.667 | **0.607** |
| Asymmetric (FP32 query, rank docs) | 0.600 | 0.600 | 0.667 | 0.607 |
| Sign-Cosine (1-bit) | 0.550 | 0.800 | 0.333 | 0.571 |
| BM25+Dense RRF | 0.450 | 0.600 | 0.667 | 0.500 |
| BM25+RankCos RRF | 0.500 | 0.600 | 0.667 | 0.536 |
| BM25+Asym RRF | 0.500 | 0.600 | 0.667 | 0.536 |

### Key Findings

1. **Rank-cosine exactly matches dense FP32 on paraphrase (0.600).** The ordinal projection preserves 100% of the retrieval signal for schema.org-typed service routing. This is stronger than Nelson's ±0.013 result on arXiv — at N=309, rank-cosine is not approximately equal to dense; it is exactly equal on this eval.

2. **BM25 collapses on paraphrase (0.300) — exactly as §5.1 predicts.** The 0.695 on arXiv paraphrase drops further to 0.300 here, likely because service descriptors are shorter (~37 tokens vs ~200 for abstracts) and share boilerplate, making BM25's term-matching signal weaker.

3. **Sign-cosine (1-bit ablation) reaches 0.550 on paraphrase.** Only 1 point behind full rank-cosine. This suggests that for schema.org-typed service routing, the *sign* of each coordinate captures most of the type-separating structure. The full ordinal resolution of RankQuant adds marginal signal on this corpus. This is the 1-bit ablation Nelson didn't run.

4. **RRF fusion hurts on paraphrase at N=309.** BM25+RankCos RRF (0.500) is *worse* than rank-cosine alone (0.600). At 207k documents, RRF smoothing helps; at 309 documents, BM25's bad rankings displace correct rank-cosine hits. **PAP should use rank-cosine as the primary channel at this scale, not fuse it with BM25.**

5. **BM25 dominates on keyword and title queries** — as expected, since these are literal substrings of the service descriptors. The hybrid value proposition is: rank-cosine for paraphrase (the default PAP use case), BM25 for exact-match (the fallback).

### Schema.org Type Clustering in Rank Space

Rank-cosine preserves schema.org type structure. Every action group shows positive intra-vs-inter separation:

| Action Type | n | Intra-group ρ | Inter-group ρ | Gap |
|---|---|---|---|---|
| SearchAction | 179 | 0.5535 | 0.4579 | +0.0956 |
| FindAction | 113 | 0.5117 | 0.4801 | +0.0316 |
| TradeAction | 4 | 0.7266 | 0.4824 | +0.2442 |
| CreateAction | 3 | 0.5882 | 0.4669 | +0.1213 |
| AnalyzeAction | 2 | 0.6466 | 0.4140 | +0.2326 |
| DatasetAction | 2 | 0.6555 | 0.4518 | +0.2037 |

SearchAction's gap (+0.0956) is modest — 179 services share vocabulary. FindAction's gap (+0.0316) is tight — the 113 FindAction services are semantically diverse (weather, packages, hotels, geocoding...). The small-group types (TradeAction, AnalyzeAction) show strong separation because their vocabulary is distinctive.

**Implication for RankQuant bucketing**: FindAction's tight intra-group similarity (+0.0316 gap) means B=2 bucketing may merge FindAction services with SearchAction services on borderline dimensions. Non-uniform bucketing (or B≥4) on type-separating dimensions would preserve the boundary.

### Storage

| Format | Bytes/vec | Total (309 agents) |
|---|---|---|
| FP32 dense | 4,096 | 1.21 MB |
| Full-rank (u16) | 2,048 | 0.60 MB |
| RankQuant-4 | 512 | 0.15 MB |
| RankQuant-2 | 256 | 0.08 MB |
| Sign (1-bit) | 128 | 0.04 MB |

At 309 agents the storage difference is trivial. At 309,000 services: 1.21 GB (FP32) vs 76 MB (RankQuant-2) vs 38 MB (sign). The advantage compounds with scale.

### Implications for PAP

1. **Rank-cosine alone is the right primitive for PAP's Level 2**, not BM25+rank-cosine RRF. The RRF fusion that works at 207k documents degrades at 309 agents. PAP should route: (1) keyword/title queries → BM25 (fast, accurate), (2) paraphrase queries → rank-cosine (semantic, accurate), (3) ambiguous → escalate to Level 3.

2. **Sign-cosine at 1 bit is a viable edge-deployment primitive.** 55% paraphrase accuracy at 128 B/vec and no FP32 arithmetic — pure XOR + popcount on sign vectors. This could run in the WASM-only browser build with no encoder needed at all (sign vectors are pre-computed at build time from the encoder's output).

3. **The 40% of unresolved paraphrase queries need a different approach.** These are the queries where neither BM25 nor rank-cosine correctly identifies the action type. They fall through to Level 3 (on-device AI). The offline CE → LambdaMART distillation recommendation from the evaluation above would close some of this gap.
